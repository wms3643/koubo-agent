# 口播剪辑 Agent 平台 · 数据库设计（生产版）

> DDL 见同目录 `schema_postgres.sql`（PostgreSQL 14+，16 张表）。
> 本文只讲**为什么这么设计** —— 面试时真正会被追问的就是这一层。

---

## 一、一句话定位

把「一个本地脚本」升级成「多用户在线服务」，需要数据库解决的只有四件事：

| 要解决的问题 | 对应设计 |
|---|---|
| 多用户数据隔离，谁也不能看谁的片 | 所有业务表挂在 `projects.owner_id` 下，查询强制带 owner 条件 |
| 剪辑方案反复改，改错要能退回去 | `transcripts` / `cut_plans` / `subtitle_cues` 全部**版本化 + is_current** |
| 渲染要花钱，网络抖动重发不能重复扣费 | `render_jobs.idempotency_key` 唯一约束 + `attempts` 重试计数 |
| Agent 跑一半崩了，重启要能接着跑 | `agent_checkpoints`（JSONB）+ `agent_runs` / `agent_steps` 审计 |

## 二、三层存储分离（最重要的一条）

```
关系数据（PostgreSQL）    大对象（S3 兼容对象存储）     Agent 状态（JSONB）
项目 / 方案 / 字幕 / 任务    视频 / 底片 / overlay / 成片    检查点 / 步骤载荷
    ▲ 要事务、要约束              ▲ 几百 MB ~ 几 GB           ▲ 结构不稳定
    │                            │                          │
    └── 只存 object_key ─────────┘                          └── 可单独归档清理
```

**为什么不把视频塞进数据库？** 一条口播源片 2 GB 起，塞进 PG 的 `bytea` 会让备份、复制、WAL 全部爆炸。库里只留 `object_key + checksum + duration_ms`，文件交给 S3 兼容对象存储（生产用云对象存储或私有化 MinIO 集群，接口协议一致、可随时换供应商，不锁定厂商）。

**存储这一层还做了四件事：**

| 手段 | 解决什么 | 对应设计 |
|---|---|---|
| **预签名 URL 直传** | 2 GB 视频不过应用服务器，避免 FastAPI worker 被上传流量占满 | 前端拿 presigned PUT，直传对象存储，完成后再回调入库 |
| **分片上传 + 断点续传** | 上传中断不用从头再来；配合 `checksum_sha256` 秒传去重 | `media_assets.upload_mode / etag` 记录分片信息 |
| **冷热分层** | 成片经常被在线播放、原片只在剪辑期用一次，存同一档位是烧钱 | `storage_class(standard / infrequent / archive)` + 生命周期规则自动沉降 |
| **CDN 回源** | 成片播放走边缘节点，不打回源站 | 库内只存 `object_key`，播放 URL 在应用层拼 CDN 域名（可随时换 CDN 商） |

**为什么检查点用 JSONB 而不是拆列？** LangGraph 的 State 结构会随节点增减而变，拆列意味着每次改图都要迁移。JSONB 让它自由演进，同时用 `UNIQUE(thread_id, checkpoint_id)` 保住幂等。

## 三、表清单（16 张，按域分组）

### 账号与项目
| 表 | 职责 | 关键约束 |
|---|---|---|
| `users` | 账号、套餐、额度 | `lower(email)` 唯一（区分软删除）、额度用「分」存整数 |
| `projects` | 聚合根，所有数据挂它下面 | `row_version` 乐观锁、`deleted_at` 软删除 |

### 素材
| 表 | 职责 | 关键约束 |
|---|---|---|
| `media_assets` | 视频/底片/BGM/overlay 登记 | `(project_id, checksum_sha256)` 唯一 → **秒传去重** |

### 转写层
| 表 | 职责 | 关键约束 |
|---|---|---|
| `transcripts` | 转写版本 | `(project_id, version)` 唯一 + **部分唯一索引**保证只有一个 `is_current` |
| `transcript_segments` | 句/词级时间戳 | `words` 用 JSONB（模型版本会变）；`(transcript_id, start_ms)` 索引 |
| `text_corrections` | 人工改字记录 | 保留 before/after，可追溯谁改的 |

### 剪辑层（简历里「双时间轴」的落库形态）
| 表 | 职责 | 关键约束 |
|---|---|---|
| `cut_plans` | 方案版本 | 版本 + `is_current` + `status(draft/approved/superseded)` |
| `cut_plan_ranges` | **保留/删除区间 = 唯一真相源** | `EXCLUDE USING gist` 禁止同动作区间重叠 |
| `timeline_maps` | 剪前 → 剪后映射 | `CHECK` 强制 src 与 dst 区间长度相等 |
| `subtitle_cues` | 字幕轨 | 按 `cut_plan_id + version` 存，改字幕不污染历史 |

### Agent 运行层
| 表 | 职责 | 关键约束 |
|---|---|---|
| `agent_runs` | 一次运行 | `thread_id` 与 LangGraph 对齐；记录 `graph_version` 便于追溯 |
| `agent_steps` | 每步：延迟 / token / 成本 | `caused_by_step` 做回退溯源 |
| `approvals` | 人工介入决定 | `decision IS NULL` 部分索引 → 快速捞出待批准队列 |
| `agent_checkpoints` | 断点续跑状态 | JSONB + `(thread_id, checkpoint_id)` 唯一 |

### 渲染与质检
| 表 | 职责 | 关键约束 |
|---|---|---|
| `render_jobs` | 渲染任务 | **`idempotency_key` 唯一** + `attempts/max_attempts` |
| `artifacts` | 产物登记（SRT/底片/成片） | `job_id ON DELETE SET NULL`，任务删了产物仍在 |
| `qc_reports` | 质检明细 | `passed = FALSE` 部分索引 → 只看异常 |

### 审计
| 表 | 职责 |
|---|---|
| `audit_logs` | 谁在什么时候改了什么（批准方案、删项目…） |

## 四、五个可以直接讲的取舍

### 1. 版本化用「多行 + is_current」，不用「update 覆盖」
```sql
CREATE UNIQUE INDEX uq_cut_plans_current ON cut_plans (project_id) WHERE is_current;
```
改方案 = 插入新版本 + 把旧版 `is_current` 置 false。好处：**任意两版可 diff**（面试官爱问「用户改错了怎么办」→ 直接切回上一版，不用重算）。
代价：表会涨。所以配归档策略（保留最近 N 版，更早的转冷表）。

### 2. 区间重叠交给数据库，不交给代码
```sql
EXCLUDE USING gist (cut_plan_id WITH =, action WITH =, int4range(start_ms, end_ms) WITH &&)
```
两个 Agent（或人和 Agent）同时改剪辑方案，很容易写出「A 区间套住 B 区间」的脏数据。这个约束让数据库直接拒绝，代码里不用再加一层校验。

### 3. 幂等键挡住重复付费
```sql
idempotency_key = sha256(project_id || cut_plan_id || spec_json)
UNIQUE (idempotency_key)
```
渲染要调付费接口，网络超时重发是最常见的重复扣费场景。同一份 spec 只允许一个 job，重发直接命中唯一约束返回已有任务。

### 4. 金额一律存「分」的整数
`quota_cents / used_cents / cost_cents` 全部 `INTEGER`，不用 `NUMERIC` 也不用 `FLOAT`。理由：对账不能有浮点误差；而且「精确到分」正好是你简历里那条理赔金额的做法。

### 5. 时间统一存毫秒整数
不使用 `INTERVAL` 或 `FLOAT 秒`。理由：FFmpeg、字幕、前端播放器底层都是毫秒整数，用它当基准就不会在换算里丢精度。

## 五、面试问答预案

**Q：为什么说这是生产版设计，你本地跑的时候用的是什么？**
> 本地是 SQLite（单文件、零运维，单人够用）。上线要解决的是多用户隔离、并发写、大文件存储、任务幂等这四件事，SQLite 的写锁模型顶不住，所以换 PostgreSQL + 对象存储。迁移成本主要在检查点表（`agent_checkpoints` 结构对齐即可）。

**Q：多租户数据隔离怎么保证？**
> `projects.owner_id` 作为隔离键，所有子表通过 project 间接归属；应用层查询强制注入 owner 条件，并给 `(owner_id, status)` 建索引保证带条件的查询仍然走索引。更严格的话可以上 PostgreSQL 的 RLS（行级安全）。

**Q：Agent 状态为什么和业务数据放同一个库？**
> 起步阶段同库省运维；但它是最容易膨胀的表（每一步都落一条 JSONB），所以设计上就把它做成**可独立拆出**的：只依赖 `thread_id`，不依赖任何业务外键，将来迁到单独的库或对象存储不影响主库。

**Q：2 GB 的源片怎么上传和存储？**
> 前端拿后端签发的**预签名 URL 直接 PUT 到对象存储**，视频流不过应用服务器；大文件走**分片上传**，`etag` 记录完成状态，断网可续传；上传前先算 `checksum_sha256`，命中 `(project_id, checksum)` 唯一索引就**秒传**（同一份素材不重复占空间）。存储按访问频率**冷热分层**：成片留在标准层供在线播放、原片转低频层、超期转归档层。播放链接由应用层拼 CDN 域名，库里只存 `object_key`，所以换对象存储或换 CDN 都不用动数据。

**Q：剪辑方案和字幕为什么要拆两张表？**
> 一个方案可以配多条字幕轨（原声字幕 / 翻译字幕 / 双语），字幕还有自己的版本生命周期（改错别字不该产生新方案版本）。拆开后两者各自版本化，互不牵连。

**Q：区间用 `start_ms/end_ms` 存，查询「第 37 秒属于哪一段」怎么办？**
> `int4range` + GiST 索引可以直接 `WHERE int4range(start_ms, end_ms) @> 37000`，配合 `= ANY` 或 `&&` 操作符走索引；配合 `timeline_maps` 还能一次查出对应的剪后时间码。

## 六、从本地方案迁到生产版的落地顺序

1. 建库 + 跑 `schema_postgres.sql`
2. 检查点：`SqliteSaver` → `PostgresSaver`（同库，`agent_checkpoints` 表即它的存储）
3. 大文件：本地 `projects/<p>/input/*.mp4` → 上传对象存储，`media_assets` 登记
4. 幂等：`kb.py render` 之前先查 `render_jobs.idempotency_key`
5. 多用户：`projects.owner_id` 接上认证中间件
